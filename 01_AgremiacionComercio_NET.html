🔷 Principios SOLID Aplicados
S — Single Responsibility
Cada clase tiene una única responsabilidad. JwtService solo genera tokens. AuthService solo autentica. ComercianteService solo gestiona comerciantes. Los controllers solo coordinan la respuesta HTTP.
O — Open/Closed
Las interfaces permiten extender sin modificar. Se puede cambiar AuthService por otra implementación (OAuth2, AD) sin tocar los controllers ni el resto del sistema.
L — Liskov Substitution
ComercianteRepository extiende BaseRepository<T> y puede usarse en cualquier lugar donde se espere un IRepository<Comerciante> sin alterar el comportamiento esperado.
I — Interface Segregation
Las interfaces están segregadas por responsabilidad: IComercianteRepository, IUsuarioRepository, IMunicipioRepository. Ninguna implementación está forzada a depender de métodos que no usa.
D — Dependency Inversion
Los servicios dependen de abstracciones (interfaces), nunca de implementaciones concretas. Todo se inyecta vía constructor a través del contenedor DI nativo de ASP.NET Core.
DI — Inyección de Dependencias
Registrado en DependencyInjection.cs por capa (Application e Infrastructure). Todos los servicios y repositorios con ciclo de vida Scoped. Configuración centralizada y llamada desde Program.cs.
🔧 Notas Técnicas — Hallazgos en Pruebas VALIDADO EN EJECUCIÓN
⚠️ EF Core + Triggers SQL Server
EF Core 8 usa OUTPUT INSERTED por defecto para recuperar el ID generado. SQL Server no permite esta cláusula cuando la tabla tiene triggers activos.

✓ Solución en ComercianteConfiguration y EstablecimientoConfiguration:
builder.ToTable("...", tb => tb.UseSqlOutputClause(false))
🔑 Migración automática de contraseñas
Los datos semilla del Reto SQL tienen contraseñas en texto plano. El AuthService detecta si es texto plano o hash BCrypt.

✓ En el primer login migra automáticamente a BCrypt.
✓ Desde el segundo login usa BCrypt.Verify() normalmente.
📊 SP Reporte — Aliases sin espacios
El SP retornaba columnas con espacios ("Cantidad de Empleados"). EF Core FromSqlRaw no puede mapearlas al DTO.

✓ Se aplicó ALTER PROCEDURE sp_ReporteComerciantes para usar aliases sin espacios compatibles con el mapeo de EF Core.
📄 CSV — Encoding UTF-8 con BOM
El CSV mostraba caracteres incorrectos en Excel (MedellÃ­n, CafÃ©).

✓ Solución: agregar BOM UTF-8 al inicio del archivo.
Encoding.UTF8.GetPreamble().Concat(Encoding.UTF8.GetBytes(...))
🔗 FluentValidation — Registro en capa correcta
AddValidatorsFromAssemblyContaining pertenece a FluentValidation.AspNetCore, paquete solo disponible en el proyecto API.

✓ Se movió el registro de Application/DependencyInjection.cs a Program.cs del proyecto API.
🔄 Connection String — Windows Authentication
En entorno local se usa Windows Authentication en lugar de usuario/contraseña SQL.

✓ appsettings.Development.json:
Server=NOMBRE_SERVIDOR;Database=AgremiacionComercio;
Trusted_Connection=True;TrustServerCertificate=True;
🐳 Docker — Swagger en Production
Swagger estaba configurado solo para Development. Al correr con Docker el ambiente es Production, por lo que Swagger no aparecía en localhost:8080.

✓ Solución: mover app.UseSwagger() fuera del bloque if (IsDevelopment) para que esté disponible en todos los ambientes.
🐳 Docker — Healthcheck sqlcmd path
La imagen mssql/server:2022-latest instala sqlcmd en /opt/mssql-tools18/bin/ en lugar de la ruta antigua /opt/mssql-tools/bin/, causando que el healthcheck fallara y la API no arrancara.

✓ Solución: healthcheck con fallback — intenta mssql-tools18 primero y si falla usa mssql-tools. Se aumentó start_period: 30s y retries: 10.
🧪 Tests — AppDbContext InMemory
El AuthService requiere AppDbContext para migrar contraseñas a BCrypt. Los tests originales no lo incluían causando error de compilación.

✓ Solución: usar UseInMemoryDatabase en tests. El usuario debe registrarse en el contexto InMemory antes del SaveChangesAsync() con ChangeTracker.Clear() posterior.
